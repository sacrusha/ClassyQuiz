Review of classyQuiz at 1e4f9d4 (read-only worktree; scratch only in .tmp/)

**Verdict.** For a teacher with one class, the happy path holds up and I found no blocker. The one finding that will bite in a real class is the stale-tablet "This quiz has finished" on the second class (#1). The sharpest limit on the owner's brief is the 5-straggler cap with no teacher override (#2). Everything else is minor or unestablished.

**What I ran**
- `npm test`: 77 of 77 pass. `npm run check`: clean. I ran both in a `git archive` copy at `.tmp/copy`, since `npm install` would write into the worktree.
- Local stack: Worker `cqreview-state`, site `cqreview-site`, ports 8851/8852, own `--persist-to`. I killed only my own processes at the end.
- `scripts/simulate.mjs` against it: 25 students, 5 on long-poll, drops, a dead tablet, a dead phone, role handover, "again". Passed.
- **State Worker killed and restarted mid-quiz (backlog: "nobody has tested it yet").**
  - Phase, question, answers, shuffled order, tokens and score all survived. A reveal after the restart scored correctly.
  - Locally the site was unusable for about 60 s afterwards (500s), which is the dev-registry artefact decisions.md already records. It says nothing about production.
  - I did not test a real deploy over open WebSockets, only the HTTP path after restart.
- Headless Edge walk: home page, paste, lobby, phone as Remote, 4 tablets, Tempo countdown (reading, Go, early close when all answered). No page errors. Screenshots are in `.tmp/probe/shots/`.
- Parser probes with typical AI output: bold markdown, A)/B) letters, negative numbers, indented lists, a stray Note, 5 answers. All handled or failed with a message the teacher can paste back to the AI.

**Findings, most important first**

1. **The second class on the same tablets hits "This quiz has finished" on its first try (verified).**
   - A tablet that played the first class keeps its token and run id in localStorage under `cq.player.<code>`.
   - Opening `/play#code` for the next class (the "Again with another class" path) gets `gone: "This quiz has finished."`: a trophy and ←.
   - The page clears the stale token, so a reload works, but with 25 children this will be most tablets.
   - Tablets still open at "Again" are told and cleared at that moment. The ones powered off between lessons are not.
   - Verified in the browser with a stale token on a running quiz. The "Again" path itself I read in code and the simulation covers it.
   - The reason is `authenticate()` in `instance.ts` plus `play.ts`. A stale token with a different run id should just become a normal join when the new run is still in the lobby. The "don't slip into the next class" case is the tablet left on the final screen, and that one the page already handles when it is told.

2. **Late joiners are capped at 5 (`MAX_LATE_JOINERS`), and the teacher cannot override it.**
   - Tablets that join after Start beyond that get "This quiz has started and takes no more players. Ask your teacher." Nothing on the teacher side lets them in.
   - The backlog says 25 children inside a minute on school tablets. Eight slow tablets would leave three stuck.
   - The Start button doesn't wait for anyone. A cheap fix is a warning at Start ("N joined") or a "let N more in" in ⋯.
   - A tablet that sleeps over 45 s mid-quiz becomes "away", and anyone can claim its avatar from "Which one are you?". That is by design, and the owner said the teacher handles it.

3. **A stray key on the projector tab starts or advances the quiz.**
   - `screen.ts` binds Space, Enter, arrows, PageDown and N to `advance`, and it works in the lobby (it begins the quiz) and also when the phone is the Remote.
   - Modifiers are not excluded. Ctrl+N advances the quiz and opens a window. Ctrl+F toggles full screen.
   - Real exposure is a teacher leaning on the laptop with students still joining.

4. **A phone Remote added after the class has joined is refused: "not once students are in".**
   - This is the owner's decision (backlog item 18), and I confirmed it behaves that way.
   - Practical effect: a teacher who forgot to connect the phone before giving out the code cannot add it. The wall's ⋯ "Steer from your phone" disappears once the first student is in.
   - The backlog "Later" item "Add remote among the wall's admin options" would fix it. It will probably be missed on day one.

5. **Smaller items**
   - **Zip with several text files.** The zip reader takes the top-level, shortest-named `.md` or `.txt` file (`unzip.ts`). A zip with `quiz.md` and `README.txt` works, but one with `notes.txt` plus `prozente-quiz.md` would pick the wrong file and fail with "no questions".
   - **Tempo line misread.** `readTempo` tests `speed|fast|points` first, so "Tempo: countdown (no points)" becomes speed. Unlikely from an AI.
   - **Letter prefixes kept.** "A) 3" keeps the letter on the tile. The guidance says no letters, and there is no warning.
   - **QR code target.** It points at `/#code`, which loads the whole guidance page before redirecting. `/play#code` would be faster on the step the owner calls slowest.
   - **Self-hosted copy.** `index.html` hard-codes `classyquiz.pages.dev` in the Build text, so a self-hosted site tells the AI to use the demo address. The Copy button does copy `location.host`.
   - **Public endpoints.**
     - `GET /api/stats` is public.
     - `POST /api/attempt` is an unauthenticated write to one Durable Object, so a loop could burn the day's allowance.
     - This is out of scope for the owner's "normal user, not malicious" brief.
   - **Docs.**
     - `docs/user-flow.md` §8 still says "uncommitted working tree".
     - `docs/bugs.md` is empty. That is accurate for known bugs, but items 1 and 2 above belong there or in the backlog.

**What holds up**
- **Scoring.** `game.ts` is a clean pure state machine; scores are computed from the stored answers, so key changes, voids and skips follow. Speed scoring uses the device's measured time, capped by the server's.
- **Late taps and doubled steps.** In-time tap acceptance and the doubled Go/Reveal guard are correct in code, and the simulation exercises them.
- **Tap loss on the teacher side.** The teacher's redraw is patched in place (`patch()` in `manage.ts`), so the earlier reviewers' tap-loss finding is fixed.
- **Layout.** `100dvh` is now used on tablets.
- **Teacher flow.** Phone Remote, wall lobby and Start look clean and readable in the screenshots. The landing page is two actions.
- **Retries and persistence.** Command retries are idempotent. Persistence survives a Worker restart.
- **Earlier review findings.** The `startRun` idempotence and `newPlayer` duplicate-avatar findings are fixed (`G.begin` guards the phase, and `newPlayer` dedupes by command id). The ping-timestamp and polling-spin findings are fixed.

**Not established**
- Real Android tablets and the school Wi-Fi.
- Durable Object CPU on the free plan for a large broadcast. I only ran 25 players locally, which does not enforce the limit.
- Production allowance-spent wording (`isQuotaError` is still a best guess).
- Free-tier Claude or other AIs reading the guidance.
- A deploy over live WebSockets.
