## Review of classyQuiz v1 at 18841fe (before first deploy)

**Method.** I read everything you listed. `npm test` passes (43) and `npm run check` is clean. I ran the local stack (wrangler dev and pages dev, state under my scratchpad, nothing deployed, no repo file changed, `git status` clean, servers stopped) and probed it with scripts in the scratchpad. Every "Verified" below is code reading, a probe against the local stack, or both. "Suspect" means reasoned from the code but not shown. Line numbers are in the file named.

### 1. Fails the purpose, a situation, or a constraint

**H1. Verified: a student device on the long-poll fallback that has no player yet hammers the server and cannot tap.**
- `instance.ts:123`: for a "chooser" the server answers the poll immediately with the `choose` message. My probe got it back in 9 ms, every time.
- `net.ts:303`: the client only sleeps when the reply was empty, so it re-polls at once. Each reply also runs `showChoose` (`play.ts:80-83, 118-145`), which rebuilds the avatar buttons many times a second.
- This hits a late joiner, or a student whose tablet died, on exactly the networks that force polling. The student's taps land on buttons being replaced, and each device burns the Pages/DO request quota until it succeeds.
- In the lobby it lasts one round trip, because `newPlayer` is sent automatically.

**H2. Verified by code: a single dead teacher device ends the lesson.**
- The teacher's secret lives only in that browser's localStorage (`dom.ts:54-62`).
- Nothing creates or shows a copyable teacher link. `/teach#id.secret` (`teach.ts:24-34`) is parsed but never produced.
- Pairing (`remote.ts`) only helps if another device already holds the quiz.
- A teacher with only a phone, whose phone dies or clears site data mid-quiz, can only re-upload. The projector and class are attached to the old instance.
- The Continuity decision still promises "the teacher view is reached through a secret teacher link"; the Pairing entry replaced the handover but not this case.

**H3. Verified: a double tap on Reveal skips the answer.**
- `teach.ts:94-100` and the bar at `teach.ts:195-198`: "Reveal" and "Next" sit in the same place. The `at` guard only helps if the second tap is sent against the old view.
- Once the first reveal is processed and the page re-renders (~100 ms), the second tap hits "Next" with a valid `at`. The class never sees the reveal.
- The same happens with "Start with a class" followed by "Start the quiz", which begins the quiz with 0 players (`teach.ts:86-91, 188-191`).

**H4. Suspect: the teacher's taps get lost while answers arrive.**
- Every answer triggers a teacher broadcast, and `teach.ts:53-59, 210, 215` replaces `main` and `actions` wholesale. The student page deliberately avoids this (`play.ts:85-92`).
- A tap whose button is replaced between touch-down and touch-up is dropped. Answers arrive fastest right when the teacher reaches for Reveal.
- In the lobby the same re-render recreates the pairing-code input on every join.

**M1. Verified: `startRun` is not idempotent, which contradicts the Transport decision.**
- The decision says "Everything a device sends is safe to repeat". `instance.ts:290-298` has no `at` guard. A second `startRun` wiped 3 joined players and rotated the code (old code now 404).
- It was also accepted mid-question and reset the run to lobby with 0 players.
- It is reachable by a resend after a lost ack. `newPlayer` has no command-id dedupe either, so a resend after a lost "welcome" creates a ghost avatar (`instance.ts:253-258`).

**M2. Suspect: the WebSocket-to-polling fallback only counts sockets that fail to open.**
- `net.ts:131-139` resets `wsFailures` on open, and `net.ts:167-179` only counts failures to open.
- A filter that accepts the upgrade and then blackholes frames makes the client reconnect forever and never poll. `/check` would report "runs over HTTP" while the real client does not.

**M3. Verified for polling, suspect for WebSockets: a device that died stays "connected", so its student cannot get their avatar back.**
- `instance.ts:31, 471-494`: a polling player counts as connected for 40 s after the last poll. A WebSocket counts as connected until the runtime closes it.
- I modified the simulator so all players poll. The revived student was not offered their avatar and became a new player; the run ended with 26 players and a lost score.
- `simulate.mjs` only exercises the clean-close case, which is why this passes there.

**M4. Verified: the request-budget figure is understated.**
- The decision "Runner: hosting shape on the Free plan" says a polled class stays around 2,500 requests.
- `instance.ts:649-653` wakes every poller on every answer, so all-poll costs roughly (answers × pollers) requests.
- Measured: 2,696 client POSTs for 25 poll-only players over 6 questions in 33 s. A 15-question lesson is about 10k Function requests and the same again on the DO side, close to the "short polling: 11,000" figure that was rejected.
- Waking only the devices whose own view changed would fix it.

**M5. Verified: the pairing loops spin when the server answers badly.**
- `net.ts:326-335`: `api()` never throws on non-JSON or 5xx. `screen.ts:91-108` and `remote.ts:27-41` then loop with no delay (no `grant`, no `expired`).
- A school filter's block page or a Cloudflare error would make a projector hammer the site.

**M6. Verified by code: shared school devices keep things beyond use.**
- Teacher secrets and quiz titles stay in localStorage until the teach page happens to receive "gone". The home page lists them without checking they still exist (`home.ts:29-36`, `dom.ts:54-62`).
- A paired projector auto-resumes the previous teacher's quiz (`screen.ts:37-40`); the "Other quiz" button is hidden in full screen.
- The key check is collapsed on a laptop, but `currentCard` shows the ticked key on a mirrored laptop. This was a declared non-target.

### 2. In front of a class
- H1, H3, H4, M2 and M3 above are the ones that would show.
- **Suspect:** the `claim` path (`instance.ts:259-263`) lets any joiner take any away avatar, as decided. Combined with M3, a child can steal the avatar of a student on a flaky connection.
- **Verified:** simulate.mjs passed 3/3 for me, plus 3 of 4 in the implementer's logs. The failed run (`.tmp/sim.log`: "s17 score 2, expected 1") was never explained. It is probably the harness checking 500 ms after the last drop, but I did not establish that.

### 3. What a stranger could do
A join code is shown on the projector and the QR code, so treat it as semi-public.

- **Unbounded newPlayer (verified).** `instance.ts:253` and `game.ts:132` have no cap. 300 players were accepted at about 11 ms each. Every join persists the whole run and broadcasts to everyone, and the projector draws every avatar.
- **Unbounded answer changes (verified).** One WebSocket client got 3,000 answer changes accepted in 10 s, each persisted (meta and run) and broadcast (`instance.ts:267-275, 362-370`).
- **Free-plan exhaustion.**
  - Verified: no rate limit on `/api/join`. 400 probes took 7 s locally, so the 90k code space can be swept. Uploads (`[[path]].ts:48-55`) and `pair/new` (300 opened in 7 s) are likewise unlimited.
  - Suspect (billing is not testable locally): the free plan's daily DO row-write and request limits are account-wide, so one client can take down every class on the site.
  - Backlog v2 item 4 defers this, but it should be a conscious launch risk.
- **Pairing typo hazard (suspect, low).** Anyone can open `role: "teacher"` pairing codes. A teacher who mistypes the 6 digits onto one hands over their secret (`directory.ts:60`, `instance.ts:392-409`). Likelihood scales with the flood.
- **Teacher rights.** I found no route to them. The secret is 192-bit and compared in constant time. A student token cannot send `reveal`, and the screen role can only `advance`.
- **Content injection (audited by reading, not rendered in a browser).**
  - Quiz text, notes, titles and answers reach the DOM only through `esc()` or `lines()` in `play.ts`, `screen.ts`, `teach.ts`, `new.ts` and `home.ts`. Everything else interpolated is a number, a digit-only code, or a server id.
  - A quiz with `<img onerror>` and `<b>` passed through the server as inert text.
  - There is no CSP (`build.mjs:20-27`), so escaping is the only layer.
  - Bidi-override characters inside text are not stripped.
- **No key leak (verified live).** The player view during a question has no counts. The screen view code carries no notes or key before the reveal.
- **Minor.** The `remove` command with player `"__proto__"` would set a property on `Object.prototype`, teacher-only (`game.ts:140-143`). HTTP body size is capped only via Content-Length, so chunked bodies reach the DO; a 40 MB chunked body returned 400 in 0.9 s.

### 4. Decisions versus code
- "Everything a device sends is safe to repeat" is false for `startRun` and `newPlayer` (M1).
- A double tap "never skips a question" is false across states (H3).
- "Stays around 2,500 requests" is understated (M4).
- "If WebSockets can't open three times, long-poll" matches the code only for failed opens (M2).
- The teacher link and "projector hands control" are gone with no replacement for a lone teacher device (H2).
- `[[path]].ts:3` comments mention `functions/_routes.json`, which does not exist. Wrangler generates it, which is probably fine; I could not confirm on a deploy.

### 5. Other surprises
- `parseQuiz` is quadratic through `answeredCount()` (`format.ts:207`). A 100-question quiz takes about 1.2 ms and a 1,000-question one about 25 ms, which is over the free plan's 10 ms CPU limit for Functions, assuming that limit applies.
- Every answer rewrites the whole `meta`, including the quiz text of up to 200 KB (`instance.ts:366`).
- `unskip` of an already-passed question counts it in the "n / total" progress but never shows it.
- Backlog items 12 (preview) and 13 (copy-back errors) are low priority. Only 13 is partly there (the copy button).

### What holds up
- **Game core and views.** `game.ts` is a small, well-tested pure state machine. Scores are computed from answers plus fixes, so key changes, voids and skips follow correctly.
- **Persistence.** The instance persists before it acknowledges, and `answer()` is a genuinely safe retry.
- **Role separation and views.** Role separation held up under probing, and views never carry the key before the reveal.
- **Lifetime.** Alarms and join-code cleanup behave as decided. Join and pairing codes are one DO each, so claims are atomic.
- **Escaping.** Escaping discipline is consistent.
- **Parser and client resilience.** The parser is forgiving and its errors are readable. The student page's redraw guard and wake handling are thoughtful. Resume by token works.
- **Tooling and documentation.** The simulator is a real chaos harness. The secrets are git-ignored. The README, deploy script and decisions log are unusually honest, which is why most findings above were checkable at all.
